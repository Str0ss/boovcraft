# Implementation Plan: Team Cohesion Analysis (Spatial, Support, Economic, Tactical)

**Branch**: `007-team-cohesion-analysis` | **Date**: 2026-05-08 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/007-team-cohesion-analysis/spec.md`

## Summary

Extend the Processor (`processor/analyze.py`) to consume the previously-untouched `events[]` stream from the parser output and emit a new top-level `team` block in `*.analysis.json` covering spatial cohesion (battle windows, army centroids, split-engagement detection vs. aura radii), support events (item-give `0x13`, missed rescues, cooperative spell casts on allies), resource cooperation (transfers `0x51` annotated with purpose hints, shared-control posture, generosity score), tactical cohesion (focus-fire on a dominant target, minimap-ping reactions `0x68`, kill participation), and a per-battle Trade-Efficiency Index with executive-summary attribution. Add a fifth tab to the React visualizer (Team), rendering the new fields entirely from JSON — no in-browser recomputation. Existing fixtures, tests, and the four shipped tabs continue to pass unchanged. Single-feature scope per the user's "all in 006" decision; staged within the feature's `tasks.md` rather than across two features.

The Processor reads `events[]` for the first time. The data probe (Phase 0) confirmed the required event-id coverage in the committed fixtures: `0x10/0x11/0x12` (movement / targeted abilities with `target: [x,y]`), `0x13` (give-item with `unit/item/target`), `0x14` (two-target abilities, candidate for spell-on-ally), `0x16` (selections), `0x51` (resource transfer — already aggregated in `players[].resourceTransfers`), `0x68` (minimap signal with `pos: [x,y]` and `duration`). Every spec requirement except cooperative spell-cast detection has its data dependency met directly; spell-cast detection is the one Phase-0 risk and ships with a degrade-to-`null` fallback per FR-029.

## Risks and Mitigation

This feature is materially larger than features 003–005 (~1900–2700 LOC of new Processor code plus ~600–900 LOC of new Visualizer code) and is the first to consume the parser's `events[]` stream beyond chat / leave-game blocks. The risks below are surfaced explicitly so each implementing PR can be reviewed against named mitigations rather than re-derived ad hoc.

| Risk | Severity | Mitigation |
|---|---|---|

**Structure Decision**: Co-locate the new Processor logic under a new `processor/team/` package (one module per concern, no shared base classes), and the new Visualizer Team-tab components under `visualizer/src/components/team/`. Keep `analyze.py` as the single Processor entry point — it grows by ~80 LOC of orchestration that calls into `team/`. Co-locate the new lookup tables (`auras.json`, `item_attributes.json`, `unit_costs.json`, `rescue_items.json`) at the top of `processor/` next to `entity_names.json` so they share the existing regeneration / review pattern.

Rationale:
- **Separate package, not flat add-ons**: ~1500–2200 LOC across six concerns is past the threshold where putting everything inline in `analyze.py` becomes hostile to review. A `team/` sub-package with one module per concern (battles / centroids / support / resources / cohesion / kills / tei / attribution) is the natural granularity. **Principle III** is honored because each module is concrete; no shared abstract `MetricComputer` base class is introduced.
- **No new top-level directory at the repo root**: keeping `parser/`, `processor/`, `visualizer/` as the only top-level layer-named folders preserves the constitution's three-layer mental model. The `team/` package is *inside* `processor/`, not a peer.
- **Lookup tables as committed JSON co-located with `entity_names.json`**: the file has a five-feature track record (001 → 005) of being the right place for committed reference data. Adding a sibling table is the cheapest possible extension.
- **One Visualizer tab is enough**: even though spec covers ~6 distinct UX components, packing them all into `TeamTab.tsx` directly would be unwieldy. A small `components/team/` folder gives each callout / list / table its own file, mirroring the existing `components/` pattern.

If implementation reveals that any of the eight Processor sub-modules naturally fold into another, the `tasks.md` step that lands them can collapse them; nothing in the plan locks the granularity in.

## Heuristic and parameter decisions

This section closes every "recorded in the plan" deferral and `[NEEDS CLARIFICATION]` marker that the spec carries. Each decision is one of: a numeric default validated against the two committed fixtures by the SC-001 zero-error bar, or a deliberately-deferred-to-Phase-0 probe (only one such — cooperative spell casts).

**Battle window detection (FR-001).** Bucket size **5 seconds**, run length floor **≥ 3 buckets** (15 s minimum to qualify as a battle), gap tolerance **≤ 2 buckets** (10 s of inactivity before the window closes). A bucket is `engaged` when at least one of the following actions, by any player, targets a unit owned by the opposite team in that bucket: `0x12` (target-position-and-unit, where `object` resolves to an opponent unit handle), `0x11` (target-position) issued by a player while a combat-capable unit is selected (selection inferred from the most recent `0x16` event), or `0x14` (two-target-positions) where either `targetA` or `targetB` is within attack range of an opponent unit. Creep aggro is excluded by ownership classification: a `0x12` action whose target unit belongs to the neutral player (slot id `12` or `15` in WC3) does not count. Single-shot harass is excluded by the run-length floor — a 5-second flicker doesn't open a battle window. The 10-second gap tolerance keeps a fight intact across brief disengagements (kiting, repositioning).

**Aura coverage table (`processor/auras.json`).** Initial entries cover the seven canonical support / buff auras: Devotion (`Hpal_AHad`, 900u), Brilliance (`Hamg_AHab`, 900u), Endurance (`Edem_AEar`, 900u), Trueshot (`Emoo_AEar`, 900u), Unholy (`Udea_AUau`, 900u), Vampiric (`Ushd_AUav`, 900u), Command (`Obla_AOcr`, 900u). Default radius when no support aura is active in a battle: **900 units** (`splitEngagement.referenceAuraId: "default"`). The table is regenerable from `w3gjs`'s ability tables via `processor/tools/build_auras.py`; ability ids are double-checked against the manual-review list in `data-model.md`.

**Split-engagement flag (FR-005).** A battle is flagged when the **maximum allied centroid distance in that battle** strictly exceeds the active aura radius from FR-004. "Maximum" because what matters is whether at least one ally is out of coverage, not the average. The two flagged ally slots are the pair achieving that maximum.

**Army centroid (FR-002) — handle-tracking approach.** The replay does not carry "where unit N is at time T" directly, but the event stream does support a position-state machine that gives per-unit last-commanded coordinates. Implementation:

1. **Unit-handle ownership map** (`processor/team/ownership.py`). Walk every `0x16` (selection) and `0x17` (hotkey-with-units) action in chronological order. For every unit handle `(a, b)` that appears in any player's selection, that handle's `owner` is set to the player's slot id. Subsequent appearances of the same handle in another player's selection are flagged as a shared-control occurrence (the original owner is preserved; the second selecting player is recorded under a `coControlledBy` field for completeness, but ownership for centroid purposes stays with the first). Neutral / creep handles are excluded by ownership being unset.
2. **Position-state machine** (`processor/team/positions.py`). Maintain a state map `{(handle): {position: (x, y), lastUpdatedMs}}`. For every command issued by a player while a selection is active: each handle in the active selection has its `position` updated to the command's `target` (`0x11`, `0x12`) or `targetA` (`0x14`). For build / train events (`0x10` with a `building`-typed `orderId`), the worker's current position becomes the new building's position; the building's handle is recovered when it next appears in a selection event (worker → building handoff). Unit deaths are inferred from the handle being absent from the player's selection for ≥ 30 in-game seconds after a move-into-combat — handled separately in `team/kills.py`, not in `positions.py`.
3. **Centroid at battle start.** For each player, the centroid is the **arithmetic mean of `position` over all handles owned by that player whose state was updated in the 60 s preceding the battle's start**. The 60-second floor filters out stale positions (a worker that has not been commanded in five minutes is probably no longer where it was last commanded; better to exclude than to mislead). If fewer than three commanded handles exist for the player in that window, fall back to the player's *single most recent* commanded position (one-handle centroid). If no command has ever been issued by that player to date (purely passive opening), the centroid is `null` and the player is excluded from split-engagement detection for that battle, with `team.battles[i].centroids[].source: "missing"`.

This is still an approximation — movement lag (the unit takes time to walk to the commanded position) is not modeled, and idle units between commands are assumed stationary. But it captures **passive defenders** that the simpler target-only centroid would have rendered as `null`, which is the case the user flagged as the reason to upgrade past Tier 1. Movement-aware simulation (Tier 3) is explicitly out of scope (Princ. III: no partial WC3 engine in this codebase). Validated against the two committed fixtures by the SC-001 zero-error bar; if a manual review of either fixture disagrees with the computed centroid in a way that materially changes the split-engagement flag, the heuristic constants (60 s window, 3-handle floor) are tuned in `tasks.md` before declaring SC-001 met.

**Item-attribute table (`processor/item_attributes.json`).** Each entry: `{ "primary": "int" | "str" | "agi" | "universal" | "none", "isRescue": bool }`. Initial coverage: every item in `entity_names.json` that is a tome, an attribute orb, a strict-attribute artifact, a healing scroll, a Town Portal scroll, a Staff of Preservation, or any other ladder-shop item that produces a missed-save in the committed fixtures. Coverage gaps surface in `diagnostics.itemAttributeGaps[]` (FR-009) and add a one-line PR to the table. Regenerator: `processor/tools/build_item_attributes.py`.

**Rescue-item list (`processor/rescue_items.json`).** Initial entries: `stwp` (Staff of Preservation), `shea` (Scroll of Healing), `stwl` (Scroll of Town Portal), `rhe1`/`rhe2` (Healing Potions), `phea` (Greater Healing Potion). Derived from `item_attributes.json` by filtering `isRescue === true`; the derivation runs in `processor/tools/build_item_attributes.py` so the two files stay in sync.

**Rescue-eligible range (FR-010).** **800 game units** at the moment of death. This matches the typical Town Portal / Staff of Preservation usage range and is conservative enough that a flag means "really could have helped." If the holder is offscreen-far, no missed save is recorded.

**Item-give recipient fit class (FR-009).** Driven entirely by the `item_attributes.json` `primary` field × the recipient hero's primary attribute (a small constant table inside `centroids.py`-adjacent module). Decision matrix: matching primary → `"good"`; mismatched strict attribute → `"wrong"`; universal items → `"neutral"`; either side absent from the table → `"unknown"` plus `diagnostics.itemAttributeGaps[]` entry.

**Resource transfer purpose hint (FR-012).** Heuristic windows: a transfer is `"tierUpAssist"` when a tier-up production event (Keep, Stronghold, Halls of the Dead, Tree of Ages, etc.) is recorded for the recipient within `[timeMs - 60s, timeMs + 60s]`; `"baseDefense"` when at least three of the recipient's buildings appear in the parser's `removeunit`-equivalent stream (`0x10/0x11/0x12` damage proxy) within the same window; `"lateGameTopUp"` when the match clock is past 75% of total duration and neither earlier classifier matched; `"none"` otherwise. The classifier is a single function in `team/resources.py`; the cutoffs (60 s, 75%) are validated against the two fixtures via SC-001.

**Generosity totalMined (FR-014).** The parser output does **not** currently expose a per-player totalMinedGold / totalMinedLumber; the data probe confirmed only `players[].apm`-adjacent totals and per-event categorization, no resource-mined accumulator. Decision: estimate `totalMined ≈ Σ (gold cost of every building + unit + upgrade in production.summary)`, treating that as a lower bound on what the player paid out (and therefore as a reasonable proxy for what they mined). The estimate is conservative — it ignores resources currently in the pile and resources spent on items — and that is acceptable because the *ratio* `(sent / estimatedSpent)` still ranks players plausibly. The decision and its caveat are surfaced in `data-model.md`; the `[NEEDS CLARIFICATION]` placeholder from the spec is hereby resolved. If a future feature adds a true totalMined to the parser output, the estimate is replaced one-for-one.

**TEI value function (FR-021).** **Gold + lumber, supply ignored.** Per the user's "Gold + lumber (supply optional)" decision. Rationale: gold and lumber are the costs the player actually spent and are uniformly available in `unit_costs.json`; supply is inventoried elsewhere and only matters for ratio-of-army-size questions, not value-of-trade questions. The formula is straightforward: `value(unit) = unit_costs[id].gold + unit_costs[id].lumber`. Supply is recorded in the table for future use but does not enter the v1 TEI numerator / denominator.

**TEI zero-loss handling (FR-021).** **Cap at `99.0`**. When `denominator === 0` (the team lost no value in that battle), TEI is set to the constant `99.0` rather than `Infinity` or `null`. This is a sentinel: it is well above any realistic finite TEI in a normal match (`base_1` peaks suggest realistic TEI is in the `0.0`–`5.0` band) and is sortable / renderable as a number without special-casing the consumer. The cap is documented in `contracts/output-shape.md` and surfaced in the Team-tab tooltip when displayed (`"≥ 99.0 — perfect trade, no own-side losses"`).

**TEI per-player formula (FR-021).** `perPlayerTei = (player_attack_share_in_window * battle_team_value_killed) / max(player_value_lost, 1)`. The `max(..., 1)` is the same cap-at-1-loss convention used in many e-sports trade indices to keep the per-player formula finite when a player lost no units while the team killed substantial value (sentinel cap at 99.0 still applies after this normalization). `player_attack_share_in_window` is the count of this player's `0x11`/`0x12` actions targeting opposing units, divided by the team's total such count in that window (this is the same numerator used by the kill-credit damage-share heuristic — see below).

**Kill-credit / KP% (FR-019).** **Damage-share by attack actions in window.** Per the user's "Damage-share по атакам" decision. The replay does not carry damage events, so the heuristic uses *attack-action share* as a proxy for damage share: each opposing unit handle that disappears within a battle window is credited fractionally to each player by their share of `0x11`/`0x12` actions targeting that handle within the 5 seconds preceding the disappearance. KP% is summed per player across all kills in a battle. If the unit's disappearance window has zero attack-action coverage from the team, the kill is unattributed and excluded from KP% (recorded once in `diagnostics.cohesionMetricGaps[]`). The choice of 5-second window is the same as the battle bucket size, deliberately aligned for consistency.

**Severity weights for executive summary (FR-023).** Base weights: split-engagement `3.0`, missed save `2.0`, low-TEI battle (TEI < 0.7 without other findings) `1.5`, shared-control-disabled `1.0`, mis-targeted item give (`recipientFitClass: "wrong"`) `0.8`, ignored ping (no `respondedBySlot[]` and no `engagedElsewhereSlot[]`) `1.2`. Each finding's weight is multiplied by `min(battle_duration_seconds / 60, 3.0)` — longer fights matter more, capped at 3× for fights past 3 minutes. The executive summary lists the top 3 by weighted severity. Ties broken by chronological order (earlier first). Weights are tuned against `base_1` and `base_2` such that the top-3 visibly reflects what a coach watching the replay would call out — validated by the SC-008 qualitative test.

**Attribution threshold (FR-022).** A blame row is emitted when ALL THREE conditions hold: (i) `splitEngagement.flagged === true` for the battle, (ii) `team.battleSummary.tei[i].teamSideTei < 1.0` (the team lost the value trade), (iii) one player's centroid is the outlier — defined as having a distance to the team's centroid mean that is greater than `1.5 * mean_pairwise_distance` for the battle. Multiple cohesion failures across the same battle yield multiple attribution rows (not collapsed); a single player can be attributed across multiple battles within one match.

**Cooperative spell-cast detection (US2 stretch / FR-029 candidate).** Per the user's "Try in 006" decision: **Phase 0 probes the parser output's `0x14` action shape** to determine whether a cast targeting an ally unit is distinguishable from a self-targeted or enemy-targeted cast. The probe checks the `owner`, `category`, and `targetA`/`targetB` fields against known ally-targeted abilities (Spirit Link, Inner Fire, Heal, Bloodlust, Faerie Fire on ally — wait, that's enemy; healing scrolls when held). If the probe confirms the data supports it, a `team.supportEvents[].type: "supportSpellCast"` entry is added per cast event, and a small ability-side table (`processor/spell_targets.json`) is committed alongside the others. If the probe shows the data is ambiguous on this point, the metric is dropped from this feature's scope, an `cohesionMetricGaps[]` entry is recorded, and a follow-up feature is filed. The probe is the first task in `tasks.md`'s Phase 0 group and is gated to occur before any code is written that would depend on its outcome.

## Phase ordering and shipping plan

`tasks.md` will encode the following phases (mapped to the user's ranking):

- **Phase 0 — Probes and tables.** Run `processor/tools/build_auras.py`, `build_item_attributes.py`, `build_unit_costs.py`. Probe `0x14` for spell-on-ally feasibility. Commit the four lookup tables. Add `processor/team/__init__.py` skeleton.
- **Phase 1a — Unit ownership and position state (Tier 2 foundation).** Implement `processor/team/ownership.py` (handle → owning playerId from `0x16`/`0x17`) and `processor/team/positions.py` (handle → last-commanded position from `0x11`/`0x12`/`0x14` plus worker→building handoff via `0x10` build orders). Both are pure event-stream walkers — no battle logic yet. Verified by `test_unit_ownership.py` and `test_position_tracking.py` against the committed fixtures; expected coverage on `base_2`: 328+ ownership entries, ~95% of `0x12` actions update at least one tracked handle's position. This phase is a hard prerequisite for centroids and is the single largest piece of new LOC in the feature.
- **Phase 1b — Battle windows + centroids + split engagement (US1).** Implements `processor/team/battles.py` and `processor/team/centroids.py` on top of Phase 1a. After this phase, `team.battles[]` exists with start/end, sides, per-player centroids (computed from positions.py state at battle start), allied pair distances, and `splitEngagement` rows. Visualizer is not touched yet; verification is via pytest + `cat team.battles | jq`.
- **Phase 2 — Support and resources (US2 + US3).** Item transfers, missed saves, optional spell-cast detection, transfer purpose hints, shared-control banner, generosity score. Independent of Phase 1's output (could land in either order, but US1 is the more impactful demo so it lands first per Phase 1).
- **Phase 3 — Tactical cohesion (US4).** Focus fire, ping reactions, KP%. Depends on Phase 1's battle windows.
- **Phase 4 — TEI + attribution + executive summary (US5).** Depends on Phase 1 and Phase 3 (TEI needs battles + per-player attack share).
- **Phase 5 — Visualizer Team tab.** All Processor work is done; the tab reads from `team.*` and renders. Plain HTML lists for most components, ECharts only on per-battle TEI bar.
- **Phase 6 — Non-regression sweep (US6).** Run all suites against both fixtures. Diff `*.analysis.json` to confirm only additive changes. Walk the existing four-tab visualizer flow against both fixtures.

Phases 1–4 land entirely on the Processor side; Phase 5 lands on the Visualizer side. Phase 6 is a final gate, not new code. Each phase ends with green pytest + green Vitest; no in-flight half-state survives a phase boundary.
